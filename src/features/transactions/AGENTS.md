# src/features/transactions/ — movimientos

- `schemas.ts` (zod, client-safe — no server imports) is shared by forms and the `/api/v1/transactions` handlers. `types.ts` holds the response DTOs. Server logic: `src/server/services/transaction.service.ts` (DB) + `transaction.logic.ts` (pure).
- **Amounts in DTOs are strings** (`"-217400"`, `"12.5"`; `Decimal.toFixed()`, no padding zeros) for `amount`, `amountBase`, `fxRate`. Exact and lossless; convert with `Number()` only for display/formatting (`formatMoney(Number(t.amount), { currency: t.currency, locale })`). Dashboard aggregates stay `number` (docs §1: "number sólo en agregados").
- Input amounts are ALWAYS positive (number or decimal string); the server signs them from `type` (INCOME +, EXPENSE −; TRANSFER − on the origin leg, + on the destination). Decimals are validated against `currencyFractionDigits(account.currency)` → COP accepts whole pesos only. Currency comes from the account; an account in a currency ≠ user baseCurrency → 400 "multimoneda aún no soportado" (no FX service yet).
- Create: `categoryId` absent → auto-categorize (suggestion ignored if its category kind ≠ type); `categoryId: null` → explicitly uncategorized. `payee` is a name; the Payee is found-or-created by `normalize(name)`. Transfers (`toAccountId`) reject `categoryId`/`payee` (strict schema). POST returns the DTO (for transfers, the origin leg; `transfer.counterpartId` points to the other).
- PATCH: transfers apply amount/date/status/description/notes/tagIds to both legs, `accountId` to the edited leg only; `type`/`categoryId`/`payee` → 400. INCOME↔EXPENSE flips the sign and drops a category of the wrong kind. Setting a different category on a transaction with a payee calls `recordCorrection()` (learning). `tagIds` replaces the set.
- DELETE = soft delete (`deletedAt`), idempotent, both legs; `POST /[id]/restore` clears it (both legs) and returns the DTO — use it for the "Deshacer" toast. Deleted rows are 404 for GET/PATCH and hidden from lists.
- List: `?dateFrom&dateTo&accountIds&categoryIds&tagIds&types&q&sort=date|amount&order=asc|desc&cursor&limit` (ids repeated or comma-separated; a parent categoryId includes its children). Response `{ items, nextCursor }`; pass `nextCursor` back unchanged with the SAME sort/order (cursor is bound to the sort; mismatch → 400). `sort=amount` orders by the signed amount (`asc` = biggest expenses first). `q` is ILIKE over the trigram-indexed `description + notes` (not payee names).
- Each DTO already embeds account, category, payee, tags and, for transfers, `transfer: { counterpartId, counterpartAccount, direction }` — don't fetch them separately for the table/widgets. Both legs of a transfer are listed; collapse by `transferGroupId` in the UI if needed.
- Tests: pure logic in tests/unit/transaction-logic.test.ts; service tests in tests/unit/transaction-service.test.ts run against the real local DB (`dotenv/config`) with two throwaway users created/deleted in the test (skipped without DATABASE_URL). Follow that pattern for other DB-backed services; never touch the demo user in tests.
- UI reuse (dashboard widget, transactions table): `components/transaction-row-actions.tsx` (⋯ DropdownMenu Editar/Duplicar/Eliminar; takes `{ id, transferGroupId }` + `onEdit(id)`) and `components/transaction-sheet.tsx` (`<TransactionSheet transactionId={id | null} onOpenChange />`, one per list; loads the full DTO via `useTransaction(id)`, accounts via `useAccounts()`, categories via `useCategories()` filtered by kind; transfers hide payee/category). Mutations live in `hooks/use-transactions.ts`: `useDeleteTransaction` (optimistic: removes rows matching id OR transferGroupId from `dashboard.recent` and from every `transactions.lists()` cache, both `{ items }` and infinite `{ pages }` shapes; rollback on error), `useRestoreTransaction`, `useUpdateTransaction`, `useCreateTransaction`, and `useTransactionActions()` → `remove(target)` (toast "Movimiento eliminado" + Deshacer → restore, which waits for the in-flight DELETE first) / `duplicate(id)` (POST copy dated today, toast "Movimiento duplicado" + Deshacer → delete). Every mutation calls `useInvalidateTransactionData()`: invalidates dashboard + transactions + accounts keys and `router.refresh()` (sidebar balances are server-rendered).
- Form: `transactionFormSchema` (all strings, comma decimals allowed) in schemas.ts; pure mapping in `form.ts` (`toFormValues`, `changedFields`, `toUpdatePayload` → PATCH with only changed fields, `duplicateInput`, `matchesTarget`), tested in tests/unit/transaction-form.test.ts. Don't use react-hook-form's `formState.dirtyFields` inside the submit handler: it stays `{}` unless read during render (proxy subscription) — compare with the initial values via `changedFields`.
- Read endpoints for forms: `GET /api/v1/accounts` (`listAccountBalances`) and `GET /api/v1/categories` (`category.service.ts` → `listCategories`: active, each parent followed by its children). ACC-001 / CAT-002 add the write routes next to them. Client fetches go through `apiFetch` (`@/lib/api`), which throws the server's `{ error }` message.
